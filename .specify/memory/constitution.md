# Silvio Rodrigues's Personal Space Constitution

## Core Principles

### I. Keep It Simple

Changes MUST use the simplest approach that supports the current idea. New dependencies,
abstractions, infrastructure, or process MUST have a concrete purpose in the current work.
Complexity added for an experiment MUST be justified by what it helps explore. Simplicity keeps
this space easy to understand, change, and return to.

### II. Exploration Is the Point

Experiments with new technologies, interactions, visuals, and ways of sharing ideas are welcome.
Each experiment MUST identify what it is trying to explore; learning is a valid outcome even
when the result is discarded. An experiment MAY be kept, revised, or removed without becoming
a permanent commitment.

### III. Make It Personal

Content and design MUST reflect Silvio's interests, voice, work, or curiosity. Decisions MUST
serve his expression or exploration rather than impose a generic portfolio formula. This
project is his personal space to share with the world, and its identity MAY evolve with him.

### IV. Take Small, Reversible Steps

Work MUST be scoped to the idea being explored, with unrelated changes left for separate work.
Experiments MUST have a practical way to be revised or removed. Planning and documentation
MUST stay proportionate to the change so that process supports momentum.

### V. Keep the Space Usable

Before publishing a change, the affected content, navigation, and interactions MUST be checked
in a browser, including a narrow viewport when layout changes. Published content MUST remain
readable, and interactive elements MUST be operable by keyboard. Experiments MAY be visibly
unfinished, but known limitations MUST be clear when they affect visitors.

## Project Boundaries

This is a personal website and a place to learn by making things. No framework, visual style,
or feature set is mandated. Tools MAY change when they support a concrete experiment or simplify
maintenance. Features, dependencies, and recurring work MUST NOT be added solely to anticipate
hypothetical future needs.

## Development Workflow

For each change, briefly state the idea or question, build the smallest useful version, and
check the affected behavior. Use automated tests when they provide useful confidence for the
behavior or risk involved; small content and visual changes MAY rely on focused manual checks.
Record useful findings or maintenance needs briefly, then decide whether to keep, refine, or
remove the experiment. No separate approval ceremony is required for routine exploration.

## Governance

This constitution guides project specifications, plans, and implementation decisions. Silvio,
as project owner, MAY amend it as his goals evolve. Amendments MUST record what changed and why,
update the version and amendment date, and identify any existing work that needs adjustment.

Versions follow semantic versioning: MAJOR for incompatible principle or governance changes,
MINOR for new principles or materially expanded guidance, and PATCH for clarifications that do
not change meaning. The ratification date remains the date of first adoption.

Each specification, plan, and change review MUST briefly check alignment with simplicity,
exploration, personal expression, reversible scope, and usability. Any exception MUST state
its reason and scope in the relevant work; recurring exceptions call for a constitution review.
Review MUST remain lightweight and proportionate to the change.
